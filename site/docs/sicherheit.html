Sicherheit

Diese sechs Grundsätze stehen in CLAUDE.md als nicht verhandelbar. Jede Änderung an ihnen braucht die ausdrückliche Freigabe des Projektinhabers und wird in der Haupt-Sitzung gelesen, nicht nur im Review.

1. Der Befehlskatalog ist geschlossen

protocol.commands.CommandType enthält ausschließlich die von der Spezifikation freigegebenen Stufe-1-Befehle. Ein neuer Wert dort ist nie eine kleine Ergänzung -- er erweitert, was ein möglicherweise kompromittierter Fleet-Server einer Wohnung befehlen kann. Stufe 2 (Abschnitt 7) erst nach ausdrücklicher Freigabe des Projektinhabers, nach einer Heizsaison Betriebserfahrung.

2. Image-Quellen sind im Agenten hartcodiert, nicht in der Cloud

Die Liste erlaubter Registrierungs-Präfixe lebt als Konstante im agent-Paket. Die Cloud nennt nur Version und Digest, nie die Quelle. Kein Digest, kein Start -- "latest" oder ein Tag ohne Digest wird ausnahmslos abgelehnt.

3. Keine privaten Schlüssel in der Cloud

WireGuard- und Geräteschlüsselpaare entstehen auf der Basisstation und verlassen sie nie; die Cloud sieht ausschließlich öffentliche Schlüssel. Ein Endpunkt oder ein Modell, das einen privaten Schlüssel annimmt oder zurückgibt, ist ein Designfehler, keine Funktion.

4. Keine Mieterdaten im Klartext in der Cloud

Betriebsdaten-Backups (thermoctl-Datenbank, Zigbee2MQTT-Gerätetabelle) werden auf dem Gerät verschlüsselt, bevor sie hochgeladen werden. Die Cloud speichert nur den opaken Block und sieht nie den Schlüssel. Beim Restore verschlüsselt der Browser den vom Vermieter eingegebenen Schlüssel lokal für genau das Zielgerät; die Cloud reicht ihn nur durch und löscht ihn, sobald er abgerufen wurde oder abgelaufen ist. Gerätekonfiguration ohne Mieterbezug darf im Klartext liegen -- die beiden Backup-Arten dürfen nicht gemischt werden.

5. Der Agent ist die Sicherheitsgrenze, nicht die Cloud

Jede Prüfung, ob ein Befehl ausgeführt wird (Id schon gesehen? Ablaufzeit überschritten? Voraussetzung für eine Soll-Zustand-Änderung erfüllt?), gehört in den Agenten und wird dort durchgesetzt -- selbst wenn die Cloud etwas anderes sagt. Konkretes Beispiel: fehlt einer Wohnung die pilot_mode-Markierung, verweigert der Agent den Befehl open_access -- nicht die Fleet-Oberfläche. Eine kompromittierte Cloud kann deshalb keine SSH-Sitzung in einer Produktionswohnung öffnen.

6. Der Watchdog kennt kein Netz und keine Registry

Arbeitsteilung: der Agent lädt ein neues Image herunter und prüft seinen Digest gegen die hartcodierten Quellen (Grundsatz 2) -- der Watchdog tauscht danach nur zwischen zwei bereits lokal vorhandenen, bereits geprüften Digests. Er ist in Go geschrieben, statisch gebaut, unter 300 Zeilen -- genau deshalb, weil er das Einzige sein muss, das noch funktioniert, wenn alles andere kaputt ist. Sein go.mod bleibt ohne eine einzige Abhängigkeit, auch nicht für ein Docker-SDK "nur um die Laufzeit anzusprechen".

Was das in der Praxis bedeutet

Ein kompromittierter Fleet-Server kann: Heartbeats und Ereignisse lesen, die vier Stufe-1-Befehle schicken (die alle keinerlei Risiko tragen), und sehen, welche Wohnungen welche Version fahren.

Ein kompromittierter Fleet-Server kann nicht: einen Sollwert ändern, ein Schloss öffnen, eine andere Software starten als die hartcodiert erlaubte, einen privaten Schlüssel abgreifen, oder lesbare Mieterdaten einsehen.
